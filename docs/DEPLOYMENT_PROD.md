# Production deployment (frontend)

The Pooja Store frontend runs on the DigitalOcean droplet `skyhit-v2` (Ubuntu 24.04)
as the Next.js **standalone** server under PM2, behind nginx.

| | |
|---|---|
| Branch flow | work → `Naga/MVP` (staging, Render) → PR → `master` (production, auto-deploy) |
| Workflow | `.github/workflows/deploy-prod.yml` (push to `master` or manual "Run workflow") |
| PR checks | `.github/workflows/ci.yml` (`npm ci` + `npm run build` on PRs to `Naga/MVP` and `master`) |
| PM2 app | `poojastore-web` (`ecosystem.config.js`), runs as user `deploy` |
| Listens on | `127.0.0.1:8102`. nginx proxies the app domain to this address |
| Backend | `poojastore-api` on `127.0.0.1:8101`, deployed separately |

`next build` always runs in GitHub Actions. The 4 GB droplet only unpacks and runs the prebuilt bundle.

## Server layout

```
/var/www/prod/poojastore-frontend/
├── releases/
│   ├── <git-sha>/            # one extracted standalone bundle per deploy (newest 5 kept)
│   │   ├── server.js         # Next.js standalone server (generated by next build)
│   │   ├── ecosystem.config.js
│   │   ├── .next/ (incl. static/)
│   │   ├── public/
│   │   ├── node_modules/     # traced runtime deps only
│   │   └── .env -> ../../shared/.env   (only if shared/.env exists)
│   └── ...
├── shared/
│   └── .env                  # optional runtime-only env (not needed today)
└── current -> releases/<git-sha>
```

`server.js` in a release is the **standalone** server generated by `next build`. The repo-root
`server.js` is a different file: a dev-only custom server with a hardcoded port 3000. It is never
part of the bundle (the release root only ever contains Next's generated `server.js`).

## How the browser reaches the API

* All client code calls **same-origin** `/api/...` paths (`lib/api.js`, `lib/session-timeout-context.js`).
* `next.config.js` rewrites `/api/:path*` to `${NEXT_PUBLIC_API_BASE_URL}/api/:path*`, so the Next.js
  server proxies the request to the backend. The browser never talks to the API host directly, so no CORS is needed for these calls.
* `NEXT_PUBLIC_API_BASE_URL` is read **at build time** and baked into the build output
  (`.next/routes-manifest.json` and any client bundle that references it). Changing the API URL
  therefore needs a **rebuild and redeploy**. Editing `shared/.env` on the server does not change it.
* A production build with the variable unset fails on purpose:
  `NEXT_PUBLIC_API_BASE_URL is not set. It is required for production builds ...`.
  Only `next dev` (`NODE_ENV=development`) falls back to `http://localhost:8000`.
* Since the server proxies to the API, set `PROD_API_URL` to an address the droplet can reach.
  Use the public API domain (e.g. `https://api.<domain>`), or `http://127.0.0.1:8101` to keep the proxy on the box.

## GitHub configuration (Settings → Secrets and variables → Actions)

| Name | Kind | Value |
|---|---|---|
| `PROD_API_URL` | **Variable** (or secret) | Production API base URL, no trailing slash, e.g. `https://api.<domain>` |
| `PROD_SSH_HOST` | Secret | Droplet IP or hostname (`168.144.152.228`) |
| `PROD_SSH_USER` | Secret | `deploy` |
| `PROD_SSH_KEY` | Secret | Private key (OpenSSH format) whose public key is in `~deploy/.ssh/authorized_keys` |
| `PROD_SSH_KNOWN_HOSTS` | Secret | **Required.** The droplet's host key line(s), e.g. output of `ssh-keyscan -t ed25519 168.144.152.228`. Verify the fingerprint against `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` on the droplet |
| `PROD_SSH_PORT` | Secret (optional) | SSH port, default `22` |

Create a dedicated deploy key pair for CI. Don't reuse a personal key:

```bash
ssh-keygen -t ed25519 -C "github-actions-poojastore-frontend" -f ./gha_poojastore_web -N ""
# append gha_poojastore_web.pub to /home/deploy/.ssh/authorized_keys on the droplet
# paste the private key gha_poojastore_web into the PROD_SSH_KEY secret, then delete the local copies
```

## What a deploy does

1. Checkout, Node 20 (npm cache), `npm ci`.
2. `NODE_ENV=production NEXT_PUBLIC_API_BASE_URL=$PROD_API_URL npm run build`.
3. `scripts/deploy/assemble-standalone.sh release.tgz`: copies `.next/static` → `.next/standalone/.next/static`,
   `public/` → `.next/standalone/public`, adds `ecosystem.config.js`, strips any `.env`, packs a tarball.
4. Uploads the tarball and `scripts/deploy/remote-deploy.sh` over SSH, then runs the script on the droplet. The script:
   * extracts to `releases/<sha>/` (uses `<sha>-<timestamp>` if that SHA is already live)
   * links `shared/.env` into the release if it exists
   * atomically switches `current` (`ln -sfn` + `mv -T`)
   * `pm2 startOrReload current/ecosystem.config.js --only poojastore-web --update-env` (starts on the first deploy) and `pm2 save`
   * polls `http://127.0.0.1:8102/` and `/login` for up to 60 s, expecting HTTP 200
   * on failure: prints the last PM2 logs, switches `current` back to the previous release, reloads, deletes the failed release and **fails the job**
   * keeps the newest 5 releases
5. Deploys are serialised (`concurrency: deploy-prod-frontend`, never cancelled mid-flight).

## First deploy (one-time server prep)

As a sudo user on the droplet:

```bash
sudo mkdir -p /var/www/prod/poojastore-frontend/{releases,shared}
sudo chown -R deploy:deploy /var/www/prod/poojastore-frontend
```

Then as `deploy`, confirm PM2 is the systemd-managed instance (`pm2-deploy`):

```bash
sudo -iu deploy
pm2 ls            # poojastore-web appears after the first deploy
```

Set the GitHub secrets and variables above, then either merge a PR into `master` or run
**Actions → Deploy production → Run workflow**. The first run starts `poojastore-web` and runs `pm2 save`,
so the systemd unit restores it after a reboot.

nginx (configured separately) should proxy the app domain to `http://127.0.0.1:8102` and pass
`Host`, `X-Forwarded-For` and `X-Forwarded-Proto`.

## Manual rollback

```bash
sudo -iu deploy
cd /var/www/prod/poojastore-frontend
ls -1t releases/                      # newest first
readlink -f current                   # what's live now
ln -sfn "$PWD/releases/<previous-sha>" current.tmp && mv -Tf current.tmp current
pm2 startOrReload current/ecosystem.config.js --only poojastore-web --update-env && pm2 save
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8102/login   # expect 200
```

To roll forward again, re-run the workflow for the desired commit, or point `current` back the same way.

```bash
NODE_ENV=production NEXT_PUBLIC_API_BASE_URL=https://api.example.invalid npm run build
bash scripts/deploy/assemble-standalone.sh
cd .next/standalone && PORT=8102 HOSTNAME=127.0.0.1 node server.js
# curl http://127.0.0.1:8102/ and /login -> 200
```
